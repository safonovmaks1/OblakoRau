# OblakoRau 2.0 — Architecture

**Статус:** проект спецификации
**Версия:** 2.0
**Архитектурный подход:** модульный frontend с независимым слоем данных и адаптерами интеграции.

---

## 1. Цель проекта

OblakoRau 2.0 — самостоятельный frontend интернет-магазина, который в перспективе должен поддерживать реальные заказы, авторизацию, оплату, доставку и интеграцию с различными CMS или собственным backend.

Новая версия не является техническим обновлением старого Gulp-проекта. Старый проект используется только как источник контента, изображений и бизнес-сценариев.

Основные требования:
- современный premium-дизайн;
- адаптивность;
- модульность;
- независимость компонентов;
- отсутствие конфликтов между страницами;
- расширяемость;
- тестируемая бизнес-логика;
- возможность подключения разных источников данных;
- пригодность итоговой сборки для последующей интеграции с CMS.

## 2. Технологический стек

| Задача | Технология |
|---|---|
| Сборка и dev server | Vite |
| Разметка | HTML5 |
| Стили | SCSS |
| Логика | Vanilla JavaScript ES Modules |
| Шаблоны | Handlebars |
| Начальные данные | JSON Mock API |
| Хранение временных данных | Storage adapter |
| Тестирование | Node.js Test Runner |
| Версионирование | Git |

React не используется на первом этапе: итоговая сборка должна предоставлять обычные HTML-страницы и отдельные CSS/JS-файлы, которые можно адаптировать для CMS.

## 3. Архитектурные принципы

### 3.1 Разделение ответственности

Каждый модуль решает одну задачу.

Примеры:
- каталог отвечает за получение и отображение каталога;
- корзина отвечает за позиции и их количество;
- checkout отвечает за процесс оформления заказа;
- авторизация отвечает за сессию покупателя;
- адаптер отвечает за связь с конкретным источником данных.

### 3.2 Независимость от CMS

Внутренний код не должен обращаться напрямую к API WooCommerce, OpenCart или 1С-Битрикс.

Все внешние запросы проходят через адаптеры.

### 3.3 Единая модель данных

Внутренние сервисы используют модель, описанную в `DATA-MODEL.md`.

Внешние данные преобразуются в неё на границе адаптера.

### 3.4 Изоляция страниц и компонентов

- Общие стили ограничиваются токенами, reset и базовой типографикой.
- Стили компонентов принадлежат компонентам.
- Стили страниц изолируются через корневой класс страницы.
- Не использовать глобальные селекторы для стилизации отдельных страниц.
- JavaScript инициализируется только там, где он нужен.

### 3.5 Безопасность

Frontend не является доверенной стороной.

Backend обязан:
- проверять входные данные;
- пересчитывать цены;
- проверять остатки;
- проверять права доступа;
- валидировать промокоды;
- подтверждать оплату по серверному событию провайдера;
- защищать персональные данные.

## 5. Слои приложения

### 5.1 Presentation layer

Отвечает за:
- HTML-разметку;
- отображение данных;
- пользовательские события;
- состояния загрузки;
- пустые состояния;
- сообщения об ошибках;
- адаптивное поведение.

Presentation layer не должен самостоятельно рассчитывать цены, резервировать остатки или создавать заказы.

### 5.2 Application layer

Организует пользовательские сценарии:
- загрузка каталога;
- просмотр товара;
- добавление в корзину;
- оформление заказа;
- вход и регистрация;
- работа с избранным.

### 5.3 Domain layer

Содержит бизнес-правила:
- идентичность позиции корзины;
- расчёт количества;
- правила доступности;
- правила выбора варианта;
- расчёт предварительной суммы;
- правила валют;
- проверки состояния заказа.

Бизнес-правила не должны зависеть от DOM, Vite, Handlebars или конкретной CMS.

### 5.4 Data layer

Отвечает за:
- получение данных;
- сохранение данных;
- преобразование ответов;
- обработку ошибок;
- взаимодействие с API.

## 6. Адаптеры данных

### 6.1 Mock adapter

Первый источник данных — JSON.

Он должен реализовывать тот же интерфейс, что и будущие CMS-адаптеры.

Пример контракта каталога:

```js
export function createCatalogAdapter(provider) {
  return {
    getProducts: (params) => provider.getProducts(params),
    getProductBySlug: (slug) => provider.getProductBySlug(slug),
    getCategories: () => provider.getCategories(),
    getBrands: () => provider.getBrands(),
  };
}
```

Пример контракта корзины и заказа:

```js
export function createCommerceAdapter(provider) {
  return {
    getCart: () => provider.getCart(),
    updateCart: (payload) => provider.updateCart(payload),
    createOrder: (payload) => provider.createOrder(payload),
  };
}
```

Это иллюстративные контракты. Финальные интерфейсы уточняются при реализации соответствующих сервисов.

### 6.2 WooCommerce adapter

Будущая интеграция с WooCommerce должна преобразовывать:
- товары;
- вариации;
- категории;
- атрибуты;
- цены;
- остатки;
- покупателей;
- корзину;
- заказы.

Нельзя распространять WooCommerce-специфичные поля по компонентам приложения.

### 6.3 OpenCart adapter

Отдельный адаптер преобразует структуру OpenCart в общую модель OblakoRau.

### 6.4 Bitrix adapter

Отдельный адаптер отвечает за соответствие внутренней модели структурам каталога, торговых предложений, цен, складов и заказов 1С-Битрикс.

### 6.5 Собственный backend

Архитектура не должна исключать собственный API.

Он может стать основным источником данных, если потребуется полный контроль над заказами, оплатой, остатками и бизнес-логикой.

## 7. Ключевые сервисы

### Catalog service
Получение товаров, категорий, брендов, фильтрация, сортировка и поиск.

### Pricing service
Работа с ценами, валютами, форматированием и правилами скидок.

### Currency service
Выбор валюты, список доступных валют, курсы и правила округления.

### Inventory service
Проверка доступности и получение информации об остатках. Реальное резервирование — только на backend.

### Cart service
Единое состояние корзины, добавление, изменение количества, удаление, очистка и подписка на изменения.

Идентичность позиции корзины определяется парой `productId + variantId`.

### Favorites service
Добавление, удаление, получение и синхронизация избранного.

### Auth service
Регистрация, вход, выход, восстановление пароля и состояние сессии.

Оформление заказа доступно только авторизованному покупателю.

### Checkout service
Подготовка данных заказа, проверка пользовательского ввода и взаимодействие с backend для создания заказа.

### Orders service
Получение списка заказов, подробностей и статусов.

## 8. Правила корзины

Корзина является единственным источником состояния позиций в интерфейсе.

Запрещено:
- хранить отдельное независимое количество в карточке товара;
- считать итоговую сумму из текстовых DOM-элементов;
- дублировать бизнес-логику корзины в checkout;
- изменять состояние только визуальным переключением кнопки.

Все компоненты получают состояние через Cart service.

Локальное хранилище используется как кэш или временное хранилище, но не как подтверждение заказа.

---

## 9. Валюты и цены

Мультивалютность закладывается с первого этапа.

Правила:
- валюта отображения хранится в настройках пользователя или приложения;
- суммы хранятся в минимальных денежных единицах;
- форматирование выполняется отдельным Currency service;
- цены не парсятся из HTML;
- курс валют не зашивается в компоненты;
- при создании заказа backend повторно рассчитывает итоговую сумму;
- заказ сохраняет валюту и цены на момент оформления.

---

## 10. Варианты и остатки

Варианты товара могут включать размер, цвет, материал и другие характеристики.

Карточка товара должна работать с выбранным вариантом, а не только с основным товаром.

Правила:
- вариант имеет собственный SKU;
- вариант имеет собственную цену или ссылку на ценовую запись;
- вариант имеет собственный остаток;
- нельзя добавить недоступный вариант;
- изменение варианта должно обновлять цену, наличие и доступные изображения при необходимости;
- остатки и резервирование окончательно контролируются backend.

---

## 11. Авторизация и checkout

Заказ без регистрации не поддерживается.

Пользователь должен:
1. создать аккаунт или войти;
2. выбрать адрес доставки;
3. выбрать способ доставки;
4. выбрать способ оплаты;
5. проверить заказ;
6. подтвердить оформление.

Frontend не должен считать заказ оформленным до получения успешного ответа backend.

---

## 12. CMS и итоговая сборка

Vite используется для разработки и сборки.

Итоговый `dist/` должен содержать:
- HTML;
- CSS;
- JS;
- изображения;
- шрифты;
- другие необходимые статические ресурсы.

Интеграция с CMS не является автоматической.

Для каждой платформы потребуется отдельная работа:
- подключение шаблонов;
- маршрутизация;
- получение данных;
- обработка форм;
- авторизация;
- корзина;
- оформление заказа;
- SEO и метаданные;
- проверка работы CMS.

Нельзя привязывать внутреннюю логику к конкретному способу вывода шаблонов CMS.

## 13. SCSS и CSS

Принципы:
- BEM;
- изоляция компонентов;
- изоляция страниц;
- общие design tokens;
- отсутствие глобальных стилевых конфликтов;
- адаптивность mobile-first;
- минимальное использование `!important`;
- никаких случайных зависимостей между страницами.

Пример:

```text
styles/
├── tokens/
├── base/
├── layout/
├── components/
└── pages/
    ├── home/
    ├── catalog/
    ├── product/
    ├── cart/
    └── checkout/
```

Стили конкретной страницы подключаются только к соответствующей странице.

---

## 14. JavaScript

Использовать ES Modules.

Запрещено:
- глобальные переменные приложения;
- единый огромный `main.js`;
- глобальная инициализация всех модулей на всех страницах;
- дублирование логики;
- зависимость бизнес-логики от конкретных HTML-классов;
- прямые запросы к CMS из компонентов.

Инициализация страницы должна быть отдельной.

Общие сервисы должны иметь явные интерфейсы и зависимости.

## 15. Тестирование

Тесты добавляются по мере появления бизнес-логики.

Приоритет:
1. Cart service.
2. Pricing и Currency services.
3. Product variant selection.
4. Inventory rules.
5. Favorites service.
6. Checkout validation.
7. API adapters.
8. Page integration.

Проверять:
- корректность данных;
- граничные значения;
- отсутствие отрицательных остатков;
- синхронизацию корзины;
- поведение при ошибках API;
- недоступность товара;
- изменение цены;
- разные валюты;
- отсутствие конфликтов между страницами.

## 16. Производительность, SEO и доступность

Обязательные требования:
- семантическая HTML-разметка;

- доступное управление с клавиатуры;

## 18. Критерии качества

Функция считается готовой, если:
- работает на предусмотренных страницах;
- не ломает другие страницы;
- не дублирует бизнес-логику;
- корректно обрабатывает ошибки;
- имеет состояния загрузки и пустого результата;
- проверена на мобильных разрешениях;
- соответствует модели данных;
- имеет тесты для критичной логики.

## 19. Главный принцип

**OblakoRau — самостоятельный продукт, а не набор страниц, привязанный к одной CMS.**

Дизайн, интерфейс, бизнес-правила и модель данных должны оставаться независимыми от конкретного backend.

Замена JSON Mock API на WooCommerce, OpenCart, 1С-Битрикс или собственный API должна происходить через адаптеры, а не через переписывание компонентов каталога, корзины и оформления заказа.
